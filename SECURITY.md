# Security

Every third-party skill or plugin in this harness, copied or linked, went through the `third-party-install-guard` review before it was added: fetched without running, scanned for risky patterns, checked with an antivirus pass, and every file that runs on its own (hooks, install scripts, agent instructions) read by hand.

A verdict covers the version listed, on the date listed. Newer versions are not covered until reviewed again. The companion plugins in `.claude-plugin/marketplace.json` are pinned to these exact commits, so enabling them installs the reviewed code.

## What the harness itself runs

- `hooks/session-start` (Claude Code only): reads `ROUTING.md` from this repository and prints it with the plugin's folder path. No network, no writes.
- `hooks/install-gate` (Claude Code only, before each shell command): if the command installs or runs third-party code (`npm install <package>`, `npx`, `pip install`, `curl … | sh` and the like), it makes Claude Code ask you first and reminds the agent to run the `third-party-install-guard` review. It never blocks or runs anything, and installs from an existing lockfile pass. No network, no writes. Off with `MAKKOV_HARNESS_INSTALL_GATE=off`.
- `install/` scripts: copy files from this repository into the agent's folders. No downloads. Everything under a project's `.makkov-harness/` (manifests, backups, the lock) and its skills folder may have come with a cloned repository, so the installers treat it as untrusted: they follow no link there (a skills folder or harness folder that is a link stops them before any change), make their backup copies with an exclusive create, and remove or move a folder a manifest names only when it is a plain skill name with a `SKILL.md` in it. For Cursor, a copy of the rule in `backups/original/` that no install recorded is never put back.
- `cloud/setup-design-tools.sh` (optional, Claude cloud environments only): installs ffmpeg from Ubuntu and two pinned npm packages with `--ignore-scripts` and `--before` the review date, so their dependencies resolve only to versions published by then. Runs only if you paste it into your environment's Setup script, or when you say yes to the agent's offer in a cloud session.
- `.github/workflows/upstream-watch.yml` (GitHub only, weekly): reads the upstream repositories of the pinned companions through the GitHub API and updates one issue in this repository. It cannot change a pin or any file. It writes only the issue it opened itself (created by `github-actions[bot]` and labelled `upstream-watch`) and escapes upstream text in the workflow commands it prints. No workflow keeps the checkout's token on disk (`persist-credentials: false`).
- `skills/design-score/` (the Design Score bundle, `mh-score.js`): runs in the page you score, inside your browser. It measures the page and shows the result in a panel of its own (one element, removed when you close it). The bundle itself makes no network requests, keeps no storage and never changes the page's own content. When an agent loads it from GitHub Pages, the script tag carries the bundle's SRI hash (sha384, checked in CI against the built file), so the browser runs only the bundle this release ships and refuses anything else. Its optional Node runner (`scripts/score.mjs`) drives a Chrome you already have through a puppeteer-core you already have, and installs nothing. It runs the probe in a DevTools isolated world that the page's scripts cannot reach, checks every field it gets back (types, ranges, lengths) and builds DESIGN.md, the fix prompt and the HTML report in Node; the report carries no script but its own. With a browser tool or the bookmarklet the probe runs in the page's own JavaScript, so the page can change the result: treat that output as untrusted. As root on Linux, Chrome runs with `--no-sandbox`, and the runner says so.
- The Design Score bookmarklets ([score.html](https://makkov-design.github.io/makkov-harness/score.html)): the loader makes one request, to this repository's GitHub Pages, for `score/mh-score.js` (the latest version) as it is published there at that moment, loads nothing else and removes its script tag once the bundle has loaded. It is not pinned to a version: the `?v=` in its address only refreshes caches. Every version also stays published, unchanged, at `score/<version>/mh-score.js`; that is the copy an agent loads, with its SRI hash. The request is sent with no referrer, so GitHub sees it like any visit (your IP address) but not the address of the page you score. Nothing the page contains and nothing Design Score measures is sent. The offline bookmarklet and the console snippet carry the whole bundle, make no request and run exactly the code you saved.
- No skill here sends data anywhere unless the user asks for a task that needs it.
- Content a skill fetches or reads (web pages, repositories, registries, HyperFrames templates and items, uploaded files, report sources) is data, never instructions. A step in it that installs something, sends data, reads credentials or edits agent configuration is not done and is reported to the person. harness-onboarding writes the personal layer only to the agent's known instructions file inside the project or home, never to a path a manifest names.
- Updates to pinned third-party code wait before they are taken (none for a fix to an advisory that affects us, 3 days for a signed or attested minor or patch release from a large publisher, 7 to 14 days otherwise), and then get the full review.
- The npm package contains no tests or test fixtures.
- Telemetry, in one place: the routing map, the installers and Design Score send none. The bundled `media-use` (copied from HeyGen's hyperframes skills) can send coarse usage events to PostHog, linked to your HeyGen account when you are signed in; in this harness that is off unless you set `MEDIA_USE_TELEMETRY=1`. The Hyperframes CLI sends its own usage events by default; when the harness's video skills start it, they set `HYPERFRAMES_NO_TELEMETRY=1` unless you set `MEDIA_USE_TELEMETRY=1`. When you run it yourself, or through the cloud setup script, set `HYPERFRAMES_NO_TELEMETRY=1`. Impeccable, an optional companion, has telemetry on by default (`impeccable telemetry off`).

The website is not part of what you install. It counts page views with GoatCounter (no cookies, no personal data, a pinned script checked with Subresource Integrity) and loads its fonts from Fontshare and Google Fonts, which see your IP address like any font request; the Design Score bundle and the bookmarklets never load it. The same verdicts, searchable and with what each piece runs, sends and needs, are on the [security index](https://makkov-design.github.io/makkov-harness/security.html).

## What the install guard is, and what it is not

The `third-party-install-guard` skill is a review procedure for the agent: pin down exactly what is being installed, fetch it without running it, scan it, read every hook and install script by hand, give a Green, Yellow or Red verdict, and install only the reviewed version, pinned. In Claude Code, `hooks/install-gate` adds a technical step: a command that installs or runs third-party code turns into a question to you, with a reminder to run the review.

What it does not do:

- It is not a sandbox. Code that you approve runs with your permissions, like any install.
- It cannot see code that a package downloads later, at run time; the review says so when it finds such downloads, and rates them Yellow at best.
- The scanner is a tripwire, not a verdict: it misses anything clever, and its findings are read by hand.
- In other agents (Codex, Cursor, Gemini CLI and the rest) the skill is instructions only; there is no hook there. Keep each tool's own approval prompt for shell commands on.
- The gate matches common install commands. A determined or compromised agent can still find another way; it raises the bar, it is not a wall.

For more assurance: keep shell commands on "ask" in your agent's permission settings, install per project rather than globally, and run agents that install things for you in a container or a virtual machine.

Open an issue, or for anything sensitive use GitHub's private vulnerability reporting on this repository. Please do not post working exploits in public issues.
